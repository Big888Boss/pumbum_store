# CSP and capacity audit 2026-07-11

Scope: production storefront at `https://477477.ru`, its Next.js runtime, storefront nginx route, container limits, disk use, and Docker log growth. Open WebUI and port `8443` are explicitly excluded and were not changed.

## Security issue

The storefront nginx policy allowed `unsafe-inline` for scripts and styles. That preserved compatibility but weakened CSP against injected script and style content.

## Implemented policy

- Generate a cryptographically random nonce per HTML request in middleware.
- Send one enforcing application CSP header; remove the old static nginx CSP.
- Require the nonce for application scripts and styles and use `strict-dynamic`.
- Block script attributes with `script-src-attr 'none'`.
- Allow only two audited Next.js route-announcer style attributes by exact SHA-256 hashes.
- Keep Yandex Metrika and map origins explicit, including the Metrika WebSocket transport.
- Escape JSON-LD script-breaking characters and attach the request nonce.
- Replace unoptimized Next image output that emitted inline styles with a typed native image component.
- Accept bounded CSP reports at `/api/csp-report`; payloads are size-limited and query strings are removed before logging.
- Keep production free of `unsafe-inline` and `unsafe-eval`; development-only compatibility does not affect the production image.

## Capacity result

- Production root disk before cleanup: `79%`, about `4.3G` free.
- Removed only identified inactive storefront images and unreferenced Docker build cache; active and rollback images were preserved.
- Final root disk after release and log rotation: `64%`, about `7.3G` free.
- Found an unbounded VPN container JSON log at about `243M`. Installed `/etc/logrotate.d/docker-containers`; the first rotation compressed it to about `22.9M` without restarting the VPN or storefront.
- New storefront container: `384 MiB` memory limit, `0.75` CPU, `256` PIDs, read-only rootfs, `cap_drop: ALL`, `no-new-privileges`, localhost-only `127.0.0.1:3012` publication.
- Observed storefront memory after cutover: about `187-210 MiB`; OOM false; restart count zero. Host available memory fluctuated between about `139` and `409 MiB` during post-release checks, with about `804 MiB` of swap still in use.
- The old resident storefront was stopped after successful cutover to avoid two Next.js processes swapping each other. Its compose file and rollback image remain.

## Deployment and rollback

- Active upstream: `127.0.0.1:3012`.
- Pre-cutover backup: `/opt/plumbing_store_v2/deploy-backups/csp-20260711-precutover`.
- Rollback image: `plumbing_store_v2-v2:rollback-pre-csp-20260711`.
- Rollback container definition: `/opt/plumbing_store_v2/deploy/docker-compose.bluegreen-espa-20260710.yml`.

Rollback procedure:

1. Start the rollback container and wait for `http://127.0.0.1:3011/api/health` to report `9276` products.
2. Restore `plumbing_store.conf` from the pre-cutover backup.
3. Run `nginx -t`, reload nginx, and verify public health and a product page.
4. Stop the CSP container only after public rollback verification succeeds.

## Residual risk

- The category-render latency finding was remediated by `PERFORMANCE_RELEASE_2026-07-11.md`: paginated HTML, a low-memory category index, a bounded Node heap and a low-priority warmup timer reduced the post-warmup public p95 to about `1.03s`. The host still has only about `1 GiB` RAM and remains capacity-constrained.
- Nonce CSP requires dynamic HTML rendering, so HTML cannot use the previous full static optimization. This is an accepted security/performance tradeoff on the current Next.js release.
- Yandex Metrika remains trusted third-party JavaScript. CSP limits the allowed execution chain but cannot make compromised trusted third-party code harmless.
- Node exporter exposes disk and memory metrics over Tailscale, but the central alert rule was not verified in this deployment.

# PLAN.md — план создания нового продающего сайта «Сантехникъ» V2

## 1. Цель проекта

Создать новый сайт магазина сантехники в отдельной папке `new-store-v2/`, не меняя старый сайт и не вмешиваясь в legacy-код. Новая версия должна быть более удобной, продающей и безопасной: с сильными карточками товаров, качественными фото и документами, понятным подбором, SEO/GEO-структурой, кросс-продажами и удобной корзиной/заявкой.

Ключевой принцип: V2 строится параллельно, legacy остаётся рабочей производственной базой до отдельного решения о запуске.

## 2. Жёсткие границы безопасности

- Все новые документы, прототипы, код и исследования размещаются только внутри `new-store-v2/`.
- Нельзя менять `legacy_src/`, существующие frontend/backend-файлы, deploy-конфиги, текущие данные каталога и старую документацию без отдельной задачи и ревью.
- Источники данных legacy можно использовать только в режиме чтения на будущих этапах.
- Перед каждым релизным этапом обязательна проверка `git diff` и подтверждение, что legacy-файлы не изменены.
- Новая версия должна иметь отдельный контур разработки, тестирования и запуска.

## 3. Продуктовая стратегия

V2 должен продавать не только товар, а решение задачи клиента. Для сантехнического магазина это особенно важно, потому что покупатель часто ищет не абстрактную позицию, а комплект для монтажа, ремонта, отопления, водоснабжения или замены оборудования.

Основные сценарии:

1. Профессионал ищет товар быстро: по артикулу, бренду, диаметру, резьбе, давлению, материалу, сертификату, наличию.
2. Частный покупатель не уверен в выборе: ему нужны подсказки, понятные категории, «подходит для», комплекты и консультация.
3. Закупщик сравнивает цены, наличие, сроки поставки, документы и возможность большого заказа.
4. Монтажник собирает комплект: основной товар + совместимые фитинги, расходники, крепёж, насосы, автоматика, герметики.

## 4. Ключевые направления V2

### 4.1. Карточки товаров

Карточка товара должна стать техническим продавцом:

- крупное главное фото;
- дополнительные фото с разных ракурсов;
- технический чертёж/габаритная схема;
- фото упаковки и маркировки, если доступно;
- таблица характеристик;
- блок совместимости;
- документы: паспорт, инструкция, сертификат, декларация;
- понятное описание «для чего используется»;
- преимущества без маркетингового шума;
- подсказки по подбору;
- наличие и срок доставки;
- CTA: «В корзину», «Получить консультацию», «Запросить счёт», «Купить комплектом».

### 4.2. Каталог и подбор

Каталог должен поддерживать два способа навигации:

- по классическим категориям: трубы, фитинги, насосы, арматура, отопление, водонагреватели и т.д.;
- по задачам: «собрать водоснабжение», «заменить насос», «подключить радиатор», «монтаж тёплого пола», «ремонт санузла».

Фильтры должны быть техническими и релевантными категории: бренд, диаметр, резьба, материал, давление, температура, мощность, производительность, тип подключения, назначение.

### 4.3. SEO и GEO

Новая структура должна поддерживать поисковое продвижение по товарам, категориям, брендам и городам. Важно избегать генерации мусорных страниц.

Базовые типы страниц:

- главная;
- категория;
- подкатегория;
- бренд;
- бренд + категория;
- товар;
- подборка по задаче;
- городская посадочная страница;
- информационные статьи и инструкции;
- страницы документов/сертификатов при необходимости.

### 4.4. Кросс-продажи

Кросс-продажи должны быть не случайными, а монтажно-логичными:

- «часто покупают вместе»;
- «нужно для монтажа»;
- «совместимые товары»;
- «расходники»;
- «аналоги»;
- «лучше по характеристикам»;
- «комплект для задачи».

Для старта допустим ручной rule-based подход, затем можно подключать аналитику заказов и ML.

### 4.5. Корзина и заявка

Корзина должна быть удобной как для розничного клиента, так и для B2B/монтажника:

- быстрое изменение количества;
- сохранение корзины;
- отправка заявки без обязательной регистрации;
- запрос счёта для юрлица;
- комментарий к заказу;
- прикрепление списка/спецификации на будущих этапах;
- подсказки по недостающим комплектующим;
- видимый телефон и мессенджеры;
- понятные сроки доставки/самовывоза.

### 4.6. Безопасность

Минимальный стандарт:

- не хранить секреты в клиентском коде;
- HTTPS на production;
- защита форм от спама;
- валидация всех пользовательских полей;
- rate limiting для форм и поиска;
- безопасные заголовки;
- раздельные окружения dev/stage/prod;
- контроль зависимостей;
- резервная стратегия для данных;
- аудит перед запуском.

## 5. Фазовый roadmap

### Фаза 0. Изоляция и подготовка

Цель: подтвердить, что V2 создаётся отдельно и не ломает старый сайт.

Задачи:

- использовать только `new-store-v2/`;
- держать `SAFETY.md` как обязательное правило;
- определить владельцев решений по UX, данным, SEO, безопасности;
- зафиксировать критерии успеха;
- подготовить список источников данных, которые можно читать в будущем.

Результат:

- новая папка создана;
- правила безопасности зафиксированы;
- плановые документы лежат в `new-store-v2/docs/`.

### Фаза 1. Архитектура данных и каталога

Цель: подготовить основу для сильных карточек и SEO.

Задачи:

- описать целевую модель товара;
- определить обязательные поля карточки;
- определить поля для категорий и брендов;
- подготовить правила slug и URL;
- спроектировать нормализатор данных;
- описать отчёт о качестве данных;
- выделить пилотные бренды: VALTEC, AQUARIO, ZOTA;
- определить, какие данные отсутствуют: фото, чертежи, сертификаты, описания.

Обязательные поля товара:

- id/SKU/артикул;
- бренд;
- название;
- категория;
- краткое описание;
- полное описание;
- характеристики;
- изображения;
- документы;
- совместимость;
- аналоги;
- сопутствующие товары;
- наличие/статус;
- цена или режим «по запросу»;
- SEO title/description;
- canonical URL;
- schema.org данные.

Результат:

- понятная структура данных V2;
- список gaps по контенту;
- готовность к прототипированию карточек и категорий.

### Фаза 2. UX-прототип и дизайн-система

Цель: создать удобный путь от поиска до заявки/корзины.

Задачи:

- спроектировать главную страницу;
- спроектировать страницу категории;
- спроектировать страницу товара;
- спроектировать поиск;
- спроектировать корзину и заявку;
- определить компоненты: кнопки, карточки, фильтры, бейджи, таблицы, блоки документов;
- сделать mobile-first структуру;
- заложить доступность: читаемые размеры, контраст, keyboard navigation.

Ключевые UX-экраны:

- главная;
- каталог;
- категория;
- бренд;
- товар;
- корзина;
- быстрый запрос счёта;
- страница задачи/подбора;
- информационная статья.

Результат:

- прототипы основных сценариев;
- список компонентов;
- требования к адаптивности.

### Фаза 3. Пилот на VALTEC

Цель: на одном сильном бренде проверить качество карточек, фильтров, документов и кросс-продаж.

Задачи:

- выбрать ограниченный набор VALTEC-категорий;
- заполнить карточки по целевой структуре;
- добавить фото, характеристики, документы;
- настроить фильтры;
- добавить блоки «совместимо», «для монтажа», «аналоги»;
- проверить поиск по артикулу;
- проверить SEO-разметку товаров и категорий.

Результат:

- эталонный брендовый раздел;
- шаблон качества для остальных брендов;
- список улучшений по данным и UX.

### Фаза 4. Расширение на AQUARIO и ZOTA

Цель: проверить универсальность структуры на насосах и отопительном оборудовании.

Задачи:

- добавить сценарии выбора насосов AQUARIO;
- добавить сценарии выбора отопительного оборудования ZOTA;
- адаптировать фильтры под мощность, производительность, напор, тип оборудования;
- добавить документы и схемы;
- проверить подсказки для покупателей;
- настроить кросс-селл между оборудованием, арматурой и расходниками.

Результат:

- доказано, что V2 подходит для разных товарных групп;
- выявлены уникальные поля для категорий.

### Фаза 5. SEO/GEO и контент

Цель: подготовить сайт к органическому трафику без переспама.

Задачи:

- настроить URL-структуру;
- подготовить title/description шаблоны;
- внедрить JSON-LD Product, Offer, BreadcrumbList, Organization, LocalBusiness;
- подготовить sitemap;
- подготовить robots;
- определить whitelist городов;
- подготовить тексты для категорий и городов;
- создать контент-план статей;
- настроить canonical и noindex для технических страниц.

Результат:

- SEO-архитектура готова;
- GEO-страницы контролируемы;
- риск дублей снижен.

### Фаза 6. Корзина, заявки и коммерческие сценарии

Цель: максимизировать конверсию в заявку/заказ.

Задачи:

- реализовать корзину без обязательной регистрации;
- добавить быстрый запрос счёта;
- добавить форму консультации;
- добавить сохранение корзины;
- добавить блок «добавьте к заказу»;
- добавить подсказки по комплектности;
- подготовить сценарий B2B-заказа;
- настроить события аналитики.

Результат:

- покупатель может быстро отправить заявку;
- монтажник может собрать комплект;
- менеджер получает понятную спецификацию.

### Фаза 7. Безопасность, производительность и предпродакшн

Цель: подготовить V2 к безопасному тестовому запуску.

Задачи:

- проверить секреты и конфиги;
- настроить защитные заголовки;
- включить rate limit;
- защитить формы от спама;
- проверить зависимости;
- провести Lighthouse-аудит;
- проверить изображения и lazy loading;
- проверить мобильную скорость;
- проверить доступность;
- прогнать smoke-тесты.

Результат:

- V2 готов к soft launch;
- риски безопасности и скорости снижены.

### Фаза 8. Мягкий запуск и аналитика

Цель: проверить V2 на реальных пользователях без риска для legacy.

Задачи:

- запуск на отдельном поддомене или закрытом preview;
- noindex на тестовой стадии;
- ограниченный трафик;
- сбор метрик;
- сравнение с legacy;
- сбор обратной связи менеджеров;
- исправление проблем;
- подготовка плана миграции, если V2 успешен.

Результат:

- подтверждены UX и конверсия;
- есть данные для решения о полном запуске.

### Фаза 9. Постзапуск и ML-ready контур

Цель: подготовить развитие рекомендаций, поиска и персонализации.

Задачи:

- накопление событий поиска, просмотров, добавлений, заявок;
- анализ нулевых поисков;
- улучшение rule-based рекомендаций;
- подготовка датасета для ML-рекомендаций;
- подключение ml-intern как вспомогательного инструмента только после стабильности базового контура;
- регулярные отчёты по качеству карточек и SEO.

Результат:

- сайт улучшается на основе данных;
- кросс-продажи становятся точнее.

## 6. Dependency graph

1. Фаза 0 обязательна перед всеми работами.
2. Фаза 1 нужна до финального UI, потому что карточки зависят от структуры данных.
3. Фаза 2 может начинаться параллельно с концом Фазы 1, но без финальной верстки до фиксации полей.
4. Фаза 3 проверяет качество модели на VALTEC.
5. Фаза 4 масштабирует модель на другие типы товаров.
6. Фаза 5 зависит от стабильных URL, таксономии и карточек.
7. Фаза 6 зависит от каталога и карточек.
8. Фаза 7 идёт параллельно, но финальная проверка после появления UI и форм.
9. Фаза 8 только после SEO/security/performance gate.
10. Фаза 9 только после накопления данных.

## 7. Критерии готовности MVP

MVP V2 считается готовым для закрытого теста, если:

- есть изолированный проект внутри `new-store-v2/`;
- legacy не изменён;
- есть главная, каталог, категория, товар, корзина/заявка;
- пилотный бренд VALTEC оформлен по новой структуре;
- карточки содержат фото, характеристики, документы или отметку об отсутствии документа;
- поиск работает по названию и артикулу;
- фильтры релевантны категории;
- формы защищены и валидируются;
- есть базовая SEO-разметка;
- мобильная версия проходит ручной smoke-test;
- скорость и доступность находятся в допустимых пределах;
- события аналитики фиксируются.

## 8. Метрики успеха

Коммерческие:

- рост конверсии в заявку/заказ;
- рост кликов по телефону/мессенджерам;
- рост среднего состава корзины;
- рост добавления сопутствующих товаров;
- снижение отказов на карточках;
- снижение нулевых поисков.

UX:

- время до нахождения нужного товара;
- доля успешных поисков по артикулу;
- глубина просмотра категорий;
- использование фильтров;
- ошибки форм;
- возвраты из корзины к каталогу.

SEO:

- индексация нужных страниц;
- отсутствие дублей;
- рост показов по категориям и брендам;
- рост локальных запросов;
- CTR сниппетов;
- корректность schema.org.

Технические:

- Core Web Vitals;
- отсутствие критических ошибок JS;
- uptime preview/prod;
- успешные smoke-тесты;
- отсутствие утечек секретов;
- отсутствие изменений legacy.

## 9. Риски и меры контроля

### Риск: случайное изменение legacy

Меры:

- работать только в `new-store-v2/`;
- ревью через `git diff`;
- отдельный deployment-контур.

### Риск: плохое качество данных

Меры:

- отчёт о gaps;
- статусы качества карточки;
- приоритетная обработка топ-товаров;
- ручная модерация пилотных брендов.

### Риск: SEO-дубли из-за GEO

Меры:

- whitelist городов;
- canonical;
- уникальные тексты только для важных страниц;
- noindex для фильтров и параметров.

### Риск: холодный старт кросс-продаж

Меры:

- начать с ручных правил;
- использовать совместимость и монтажную логику;
- собирать аналитику для улучшения.

### Риск: перегруженная карточка товара

Меры:

- mobile-first;
- раскрывающиеся блоки;
- закреплённый CTA;
- приоритет: фото, цена/наличие, характеристики, документы.

### Риск: формы будут спамиться

Меры:

- rate limit;
- honeypot/captcha по необходимости;
- серверная валидация;
- логирование аномалий.

## 10. Роли и контроль качества

Минимальные зоны ответственности:

- Product/UX: сценарии покупки, структура экранов, корзина.
- Catalog/Data: нормализация товаров, характеристики, документы.
- SEO: URL, metadata, schema.org, sitemap, GEO.
- Security/Ops: окружения, секреты, rate limit, headers, деплой.
- Content: описания, инструкции, фото, сертификаты.
- Review: проверка, что legacy не изменён.
